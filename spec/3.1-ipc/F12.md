#### §3.1 · F12 IPC

<!-- split-spec IPC row -->
- **command**
  - `get_thread_menu { thread_identifier }`,
  - `run_thread_menu_action { project_identifier, thread_identifier, action }`,
  - `delete_thread { project_identifier, thread_identifier }`,
  - `delete_swarm { project_identifier, swarm_identifier }`,
  - `undo_delete_thread { deletion }`

Sidebar right-click menu and Delete with Undo (F12).
The backend builds the menu from saved state, the agent session and the workspace's measured size; on a swarm or goal swarm row it is the one Delete entry, and the menu says `swarm`.
Actions: open the workspace in Explorer, copy its path (with a toast), open the PR in the browser.
A failed pending Rosen workspace launch also offers `RetryWorkspace` (`Retry Rosen workspace`); the same `run_thread_menu_action` command retries its saved launch, never a git fallback (F5, #407).
`delete_thread` hides the thread at once and publishes a toast carrying the deletion's Undo token on `layout://state`.
Nothing is touched for 5 s.
Then the backend stops the agent, removes the workspace (the workspace lifecycle's `UserDeletedThread`), closes any named change, returns the thread's tasks to todo and drops its record.
The record always goes: a workspace that cannot be removed yet (its agent still exiting, a file still held open, or F5's verification keeping it) is saved on the project in `state.json` and retried in the background every 30 s, verified again each time, and the toast says why; a PR that will not close is reported the same way.
`delete_swarm` does this for a swarm or goal swarm and all its members under one Undo token, then removes the swarm's record; `undo_delete_thread` undoes either.
