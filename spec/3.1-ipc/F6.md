- **command**
  - `list_pull_requests { project_identifier }`,
  - `get_pull_request { project_identifier, number }`,
  - `dispatch_pull_request { project_identifier, operation }`

GitHub through signed-in `gh`: paginated PR snapshots and typed create, review, comment, reply, resolve, review-request, merge and close operations.
Create accepts `base_branch` (the project's configured branch), defaulting to GitHub's default branch.
Approve and request changes follow F7's approval record (Q28): each needs a reason, records an `approved` / `changes` event (PR number, reviewer nick, head SHA) in the project's AIRC channel, and mirrors it on GitHub as a review starting "Approved at `<sha7>`" (a comment review when the login authored the PR, which GitHub refuses to approve).
Window commands record as `you`.
Merge requires that record: the latest approval with no newer `changes`, at exactly the head being merged, which is sent to GitHub as the expected head.
GitHub's review state is not consulted.
A refused merge posts a `failed` event; a merged same-repository topic branch is deleted.
CI is advisory (F7).
F6 observes same-repository PRs by the thread's immutable branch, including a PR closed or merged between observations.
An open draft claim leaves its thread working until the PR is marked ready; a closed draft still reports closure.
The native watcher checkpoints its history and pending agent notifications in `state.json`, queues changed CI/review/conflict information at agent step boundaries, and publishes the thread lifecycle.
Closing preserves the checkout and branches; confirmed merges stop the agent and remove its verified registered worktree through the existing F5 lifecycle plan, retrying cleanup errors.
Before forced removal begins, the watcher durably records `worktree_removal_started` next to `worktree_deleted` in `state.json`, after the F17 deletion gate verifies ownership and absence of uncommitted, untracked or unpushed work.
Only that record permits retrying an unregistered leftover folder, and only while it contains no `.git` entry and does not contain the project checkout; an unregistered folder without that record is kept.
The live rail uses the independent `pr://panel` projection below.

<!-- split-spec IPC row -->
- **command**
  - `get_pull_request_panel`,
  - `open_project_pull_request { project_identifier, number }`

Backend-owned active-project PR rail.
Native refresh reads all open PRs, the current head's aggregate CI, line counts, review decision, review tier (F7, read from the PR's diff once per head against the checkout's AGENTS.md) and the first explicit claim comment: `Reviewing · <nick>` names a PR duty agent, a bare `Reviewing` its author.
A row opens its owning thread (recorded PR identity, then an unassigned matching branch from the same repository), otherwise GitHub in the browser.
Clicks validate project identity.

- **event**
  - `pr://opened`,
  - `pr://ci`,
  - `pr://review`,
  - `pr://merged`,
  - `pr://closed`

F6 lifecycle snapshots: project/thread identifiers, PR number, stage and worktree-deleted status.
`pr://merged` follows successful worktree cleanup; the layout carries the history and review cards.

<!-- split-spec IPC row -->
- **event**
  - `pr://panel`

Ordered active-project PR panel snapshots, refreshed natively after project selection and at 30-second intervals.
Loading and failed refreshes are explicit; failed refreshes retain the last rows with the error.
The UI never polls GitHub.
A refresh is one list query however many PRs are open: the project's GitHub client is kept between refreshes, a PR's comments (for its reviewer claim) are read again only when its update time or comment count moved, and its diff (for its review tier) only when its head moved.
