### 3.2 Agent protocol: ACP

Velocity is an **ACP (Agent Client Protocol) client**, as T3 Code, Zed and most other code editors are.
Every agent runs as a subprocess that speaks ACP: JSON-RPC 2.0 over stdio.
- **One process per thread**, launched in that thread's workspace.
- **Client:** the Rust backend, using the `agent-client-protocol` crate.
- **Provider code:** launch commands and provider-specific session extensions stay in the ACP client.

| Provider | ACP agent |
|---|---|
| Anthropic | Claude Code through the `claude-agent-acp` adapter (npm `@agentclientprotocol/claude-agent-acp`). Its former name, `claude-code-acp`, is deprecated and fails every prompt on a current Claude Code config (#46). |
| Codex | Codex through the `codex-acp` adapter (npm `@agentclientprotocol/codex-acp`) |
| Kimi Code | Kimi CLI's own ACP mode (`kimi acp`) |
| Antigravity | Google's own Antigravity agent: `agy acp` (Antigravity CLI 1.5.0 or later) |
| Custom | any ACP agent you add in Settings → Providers: a command and its arguments (F15) |

**Antigravity** (decided, Q14).
Velocity launches the `agy` on your `PATH` with your own `~/.gemini` profile, as it launches the other three agents (Tool access, below), with `--dangerously-skip-permissions` so it approves every tool call itself (Rule 1).
Antigravity CLI 1.5 offers no unrestricted session mode to select, so Velocity selects none.
Sign-in is the agent's own Google login, through `authenticate` or `agy acp --login`.
The model list comes from your Antigravity account.
Velocity doesn't download or pin a runtime of its own, doesn't give the agent a separate profile, and never presents itself to the agent as another client.

How Velocity's features map onto ACP:

| Velocity | ACP |
|---|---|
| Sign in (F15) | `initialize` returns the agent's `authMethods`. `authenticate` runs that agent's own OAuth login in your browser. Tokens stay in the agent's credential store. |
| Start a thread | Spawn the agent with your own config loaded (Tool access, below), and call `session/new` with `cwd` set to the thread's workspace and `mcpServers` set to AIRC plus your shared MCP servers. |
| Project instructions (#457, #534) | Ensure `AGENTS.md` is injected once, whatever the harness loads. Codex, Antigravity and Kimi Code load `AGENTS.md` natively; for Claude, Velocity skips injection when `CLAUDE.md` already imports or duplicates `AGENTS.md`, and otherwise appends `AGENTS.md` to `_meta.systemPrompt` with `claudeMdExcludes` suppressing duplicate disk loading. |
| AIRC tools for every agent (F14) | The AIRC MCP server is passed in `session/new`, so every provider gets the same tools with no per-provider setup. |
| Agent browser (F20, #488) | Build threads receive `velocity-browser` in `session/new` and `session/load`, with a tool route limited to that thread's offscreen browser. |
| Prompt, queued steering (Rule 1) | `session/prompt`. A steering message sent mid-turn is queued and sent as the next prompt when the turn ends. |
| `Esc` interrupt | `session/cancel` |
| Transcript, tool steps, diffs (F4) | `session/update` notifications: message chunks, `tool_call` / `tool_call_update` (kind, status, file locations, diff content) and plan updates |
| Slash menu (F4) | `available_commands_update` |
| Unrestricted agents, no approval UI (Rule 1) | Velocity answers every `session/request_permission` at once with the agent's allow-always option. Where an agent offers a bypass mode, Velocity selects it when the session starts. Permission requests are never shown to you. |
| Model, effort and speed | The agent's session model and config options where it exposes them, otherwise launch arguments. Whether a model has a fast mode is read from the agent's config options, not hard-coded. |
| File edits and claims (F14) | Velocity advertises the `fs` and `terminal` client capabilities, with relative paths resolved against the thread's workspace. They are not confined to it (Tool access). Edits and tool-call file locations feed the diff view and the claim checker. If an agent edits a file it hasn't claimed, the file is added to its claim, an overlap check runs, and a `claim` event is posted. |
| Resume after a restart | The transcript and ACP session id are saved in `state.json` and visible on reopening. Closing Velocity stops every running turn. When Velocity starts again, each build thread (swarm and goal swarm members included) whose turn was cut off, or whose queued messages were still unread, continues by itself with no message from you: it resumes with `session/load`, where the agent supports it, otherwise a new session receives the earlier transcript, and is told Velocity restarted, that a command it was running was stopped, and to continue where it left off. Your queued messages follow in order. A thread cut off before its agent's session started (worktree setup, goal swarm work choice) has nothing to continue and stays idle. A resume that fails (its worktree is gone, its agent can't start) fails the thread with the reason. Parked and at-limit threads resume on their own wake-ups (§2.2). Sending the next message to an idle thread resumes it the same way: the message is queued behind any earlier unread ones and the queue opens the new session. It shows as queued until the agent reads it, so a session that ends first (parked, restarted after a stall, stopped, or failing to load) sends it again on its next resume. Replayed history is not duplicated when a local transcript exists; older records with only a session id recover the provider?s replayed history when available. Saved process activity resets to idle (except parked and at-limit recovery) until the resume starts; an idle working thread appears under Done and is not counted as running. It returns to Running when it resumes; its worktree and PR watcher stay. Review workers can pick up uncovered lands after restart, and Scouts keep their saved sweep schedules (F7). |
| Rosen startup recovery (#476) | Each interrupted thread retries transient Rosen AIRC errors with the workspace-launch backoff for up to a minute and reports the last error under “Could not continue after Velocity restarted” if recovery fails. |
| Fatal process exit (#397, #543) | A small supervisor launches the window and backend in a child process. An unexpected exit, including an abort or external termination, starts a replacement automatically; its ordinary startup resumes interrupted build threads and restarts Scouts, the review swarm and post-land verification as above. Closing the window deliberately stops the supervisor too. An update hands recovery to its replacement launcher; a failed installation re-enables recovery. Exit intent travels over a private loopback connection with supervisor acknowledgement, clean write-half shutdown on final exit, and a launcher-PID marker file in `%TEMP%` so socket resets never lose a deliberate close. Recovery waits 1, 2, 4, 8 and 16 seconds between attempts, then stops after five unsuccessful restarts; five minutes of continuous running resets this budget. Launch failures share the budget. The supervisor records failures, exhausted retries, and any restart after an unannounced exit code 0 in `%TEMP%\velocity-recovery-<launcher-pid>.log`, and the next instance records unannounced exit-code-0 restarts in `velocity.log`. MCP server invocations bypass supervision. |
| Subscription limits (F15) | Not part of ACP. They are read per provider (F15 Limit sources). |

For agents with a recognized bypass mode, Velocity uses the mode config option when available and checks the value the agent returns, or uses legacy `session/set_mode` and observes any mode notification for the same session.
If an agent with a provider-defined bypass reports a mode yet no longer offers its bypass, or if a mode switch reports a restricted mode, Velocity logs the reported mode and fails the thread before the first prompt.
When Codex starts in a restricted mode, its adapter must confirm a legacy mode switch.

**Tool access.**
Every agent receives an MCP tool set scoped to its thread role (`builder`, `reviewer`, `scout`, `follow_up` or `question`), rather than every tool from every server (#533).
Forbidden or destructive tools for a role (such as `workspace_delete`, `change_abandon`, `change_recover`, `review_mark`, `review_landed`, `task_delete`, `join` and `leave` on builder threads) are omitted from `tools/list` and refused on `tools/call`.
Occasional tools for a role are loaded on demand when the provider harness supports it (Claude Code and Antigravity), using `ENABLE_TOOL_SEARCH=true` for Claude Code and a single loader tool (`rosen_tools`, `airc_tools`, `graph_tools`, `run_tools`, `browser_tools`) that emits `notifications/tools/list_changed` when inspected or invokes the occasional tool directly.
Read-only question threads (`question` role, toggled in the home composer or started with `/ask ` or `/question `) run directly against the project repository with no workspace, Rosen change, claim, browser or landable status, with write capabilities disabled.
Velocity's own MCP tool answers fit in 8,000 characters and explain how to narrow or continue an incomplete result.
Prompts generated by Velocity fit in 8,000 characters, with 4,000 for dispatch and build repair.
- **Built-in tools:** each provider's agent keeps its native coding tools, including shell, file read/write/edit, search, web search and fetch, subagents and todo/plan.
  Velocity starts agents in unrestricted mode and replaces the desktop computer-use integration with the private agent browser (F20).
- **Your own config:** each agent is launched so it loads your user and project config as it would in a terminal: its MCP servers, skills, slash commands, hooks and instruction files (`CLAUDE.md`, `AGENTS.md`).
  Velocity doesn't launch agents in an isolated or empty config.
- **Trim unused agent context** (F13, #458): launch Claude Code with claude.ai connectors, bundled skills, artifacts and workflows disabled.
  Pass Codex session overrides to skip its automatic skill catalog and ChatGPT connectors.
  Skills linked by Velocity remain available by manifest path, GitHub issue and workflow actions run through AIRC and `velocity-run` MCP tools, and both agents still load their configured MCP servers.
  Turning off the switch restores the provider's usual context while the agent browser remains the interface for page work.
- **Desktop computer use** (F20, #488): Codex app-server startup disables Desktop Computer Use and its bundled plugin before either can start.
  Claude Code session settings disable the computer-use MCP server.
  Implementation agents use `velocity-browser` for pages; non-UI builder threads receive `velocity-browser` on demand behind `browser_tools`, and reviewers, scouts and question threads omit it (#533).
- **Skills:** the project's always-on skills (F18) are linked at session start, in the folder its provider reads.
  Invoked skills are linked when the turn starts and the agent receives their manifest paths.
- **Shared MCP servers** (Settings → Agents): servers listed here are passed to every agent of every provider in `session/new`, so one list reaches all four providers.
  When a name is also in an agent's own config, the agent's own entry wins.
  A server is a command the agent starts (stdio) or a URL (streamable HTTP); it has no environment or header field, so a server that needs a credential reads it from your environment or signs in itself.
  An HTTP server is sent only to agents that advertise HTTP MCP support in `initialize`.
  Velocity reads the server names in the files each agent loads (Claude Code: `~/.claude.json` and its entry for the folder, and `.mcp.json`; Codex: `config.toml` in `CODEX_HOME` or `~/.codex`, and `.codex/config.toml`; Antigravity: `~/.gemini/settings.json`, `~/.gemini/antigravity/mcp_config.json` and `.gemini/settings.json`; Kimi Code: `~/.kimi-code/mcp.json` and `~/.kimi/mcp.json`) and leaves a clashing shared server out of `session/new`.
  New agents get the list; running agents keep the servers they started with.
- **Collapse** (#430, Collapse C9): when Collapse is connected and its switch in Settings → Agents → Shared MCP servers is on, every agent also gets the HTTP server `collapse` at `https://api.collapse.sh/mcp`.
  It follows the shared servers, so a shared server you named `collapse` wins.
  Sign in with Collapse opens Collapse's desktop sign-in (Collapse C1) in the browser: Velocity listens on a loopback port, sends an S256 PKCE challenge and exchanges the approved code for the account's read-only personal access token and provisioning token.
  Both tokens stay in the OS credential store (Windows Credential Manager entry `velocity:collapse.sh`), never in `state.json`, and the server's `Authorization: Bearer` header is read from it at each launch.
  The tools are read-only on Collapse's side, so Velocity adds no restriction of its own.
  Disconnect forgets the tokens on this machine; they stay valid on Collapse until revoked in its token list.
  The switch is on by default and reaches new agents; running agents keep the servers they started with.
- **AIRC:** always passed, filtered to the thread's role (F14, #533).
- **Code graph:** the `velocity-graph` server is always passed, beside AIRC, filtered to the thread's role (F19, #533).
  Implementation prompts cite the task's spec references or direct the agent to find relevant indexed headings with `graph_find`.
  Use `graph_read` with `source: true` on those headings and read only their lines when the graph is unavailable or the result is clipped.
- **Shell, network, toolchains:** the shell runs as you, with your `PATH`, toolchains (cargo, lake, node, python…), credentials and network.
  There is no sandbox or container.
- **Git and GitHub shims (#530, #533, #534, #563):** inside a Rosen workspace or Rosen agent environment, managed `git` and `gh` shims on `PATH` refuse at once with a one-line explanation naming the allowed Rosen, AIRC or `velocity-run` alternative (and agents do not inherit owner GitHub credentials); outside Rosen projects, `git` and `gh` pass through to the host tools.
  Direct `git` and `gh` invocations through `velocity-run` or `rosen run` are likewise refused by policy in Rosen sessions, while queued build and test commands that pass policy run without Velocity's agent shims or `VELOCITY_BLOCK_GIT_GH` so test suites invoking `git` (such as Go tests running `git init` in temp directories or `git check-ref-format`) reach the host `git` binary.
- **Workspace:** the working directory, not a jail.
  Agents can read anything on the machine, such as other repos, docs and caches.
  Their edits belong in their own workspace (AGENTS.md); edits elsewhere aren't blocked.
- **Permissions:** answered allow-always as above (Rule 1).

**Subagents** (#436).
A subagent is keyed by the parent's tool call that spawned it, or by its own session when the agent gives it one, and its messages, tool steps and diffs go to its own transcript, never the parent's.
Velocity declares native subagent sessions (`clientCapabilities.subagents`) to Codex only, because `codex-acp` forwards a child thread's own items to no other client.
Every other agent reports subagent work inside the parent session:

| Agent | Spawning call | The subagent's own updates | Status, model and tokens |
|---|---|---|---|
| `claude-agent-acp` 0.106 | `tool_call` with `_meta.claudeCode.toolName` `Agent` (`Task` in older Claude Code); raw input `description`, `prompt`, `subagent_type` and optional `model` and `run_in_background` | Every message chunk and tool call made inside the call carries `_meta.claudeCode.parentToolUseId`. A tool call's later updates stay with the subagent its first update named, because a later update can omit the stamp, such as a progress beat sent after the subagent's task settled. | The call's status; `_meta.claudeCode.toolResponse.totalTokens` on completion; `isAsync` or `status: async_launched` marks a background subagent |
| `codex-acp` 2.6 | `subagent_update` in the parent session, naming the child's session and its `title`, with its prompt as `description` when the adapter has it; no `spawnAgent` call is shown | Every `session/update` under the child's session id | `subagent_update` `state`: `running` and `requires_action` are running, `idle` is done, `idle` with stop reason `error` or `cancelled` is failed, and `unknown` fails a running subagent; the model from the child session's `config_option_update`; tokens from its `usage_update` |
| `codex-acp` without native sessions | `tool_call` titled `spawnAgent`, with raw input `prompt`, `model`, `receiverThreadIds` and `agentsStates` | Not forwarded: child threads reach the client only as approval requests | Each collab call's `agentsStates` per child thread: `pendingInit` and `running` are running, `completed` is done, and `errored`, `shutdown`, `notFound` and `interrupted` are failed; no token use |
| Kimi Code (`kimi acp`) | Not identified in its ACP output | No attribution is reported, so a subagent shows only as the parent's tool step | None |
| Antigravity (`agy acp`) | Not identified in its ACP output | No attribution is reported, so a subagent shows only as the parent's tool step | None |

A subagent runs until its spawning call completes (done) or fails (failed).
A background Claude subagent or a Codex subagent stays running after its call returns, until its thread reports an end or the session ends.
A Codex subagent that its parent messages again runs again.
A subagent session's context use, model and commands are its own and never change the thread's.
A subagent still running when its session ends failed, unless it ran in the background, which counts as done.
Its model is the one its spawning call asked for or its own session reports, or the thread's own model when neither names one.
Its edits count in the thread's line counts and claims (F14).
Subagent transcripts are live session state: `state.json` keeps only the parent's spawning step, and history replayed by `session/load` does not rebuild them.
A Codex subagent with its own session leaves no spawning step in the parent's transcript.
A subagent session known only from replayed history is listed again, with its announced title, once it reports a new message or step.
The thread view model lists the subagents with their description, model, status, start time, token use, step count, newest step and transcript blocks, and `thread://subagent` (§3.1 F4) sends each change.

**Accept when:**
- [ ] Every agent's tool list, as reported in its first `tool_call`s and available commands, matches the same agent run in a terminal with the same config, plus AIRC and the shared MCP servers.
- [ ] A shared MCP server added in Settings → Agents is available to new agents of all four providers without per-provider setup.
- [ ] No role, including duty agents and spec interviews, runs with fewer tools than a thread.
